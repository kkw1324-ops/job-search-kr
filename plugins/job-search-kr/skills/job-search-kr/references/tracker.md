# 지원 기록과 지원 계획

이 파일은 두 공정의 원본이다. 공정 8(지원 계획)은 「여러 곳 지원 계획」이 맡고, 공정 16(기록과 결과 분석)은 나머지 절이 맡는다. 결과는 `work/지원계획.md`, `tracker.md`(지원 기록 표), 지원 폴더의 `결과.md`에 둔다.

## 여러 곳 지원 계획

공정 7(`evaluate.md` 「관문」)이 그룹 중복 지원과 재지원 제한을 판정하고, 이 공정은 그 판정으로 어느 건을 낼지 고른다. 평가한 공고 가운데 이번에 쓸 건, 기다릴 건, 내려놓을 건을 정하고 쓸 건의 작업 순서와 제출 목표일을 정해서, SKILL.md 「서류 문구의 필수 과정」을 줄이지 않고 마감 안에 내게 한다. 목적은 쓸 건을 줄이는 것이 아니라 질을 지킬 수 있는 만큼 내도록 순서를 정하는 것이다. 결과는 공정 9~13의 작업 순서가 되고, 필수 과정 ①의 지원 가능 확인이 이 표와 대조한다.

**언제 만드는가:** 열린 건이 둘 이상이거나, 사용자가 제출 목록을 지정했거나, 새 건과 같은 그룹에 이미 낸 건이나 열린 건이 있으면 공정 9 전에 만든다. 마지막 경우에는 ②만 해도 된다.

| 항목 | 채울 내용 | 채우는 방법 |
|---|---|---|
| ① 건별 상태표 | 열린 건(평가함, 준비중, 어학 대기, 필기·과제)마다 회사, 직무, 그룹, 권고, 풀리지 않은 관문 표시, 게시일, 마감일, 제출 목표일, 사용자 지정 여부, 선행 공정의 준비 상태(목표 확정 여부, 자기 이해의 선행 항목, 문항 공백표, 본보기), 필수 과정의 진행 단계, 필기 전형의 준비 일정, 계획(이번에 씀, 대기, 내려놓음)과 이유 | 진행 단계는 지원 폴더의 파일과 `tracker.md`로 판정하고 기억으로 채우지 않는다. 평가 파일이 없는 「평가함」 행과 사용자가 지정했지만 아직 평가하지 않은 공고는 권고와 관문 칸에 「평가 없음」을 적는다. 작성기록이 없는 옛 지원 폴더는 진행 단계를 「옛 형식(기록 없음)」으로 적고, 그 폴더의 초안은 새로 쓸 때의 참고로만 보며 단계를 마친 것으로 치지 않는다. 선행 공정의 준비 상태는 프로필 「목표」의 상태 줄, 「자기 이해」 상태표, `profile/stories.md`의 문항 공백표, `profile/본보기/`로 판정하며 모든 건에 같은 값이므로 표 위에 한 번만 적어도 된다. 사용자 지정 여부는 `work/지정공고-<기간>.tsv`가 있으면 그 파일에서, 없으면 대화와 지원 기록 메모에서 확인한다. 게시일은 평가 파일 머리의 게시일을 쓰고, 거기에 없으면 평가 파일 머리의 공고 주소나 회사·직무로 공정 6의 본 공고 목록에서 행을 찾아 가져오며, 사이트에 없으면 비워 둔다. 마감일이 같은 건이 여럿이거나 사용자가 현황을 물으면 다른 작업보다 이 표를 먼저 보인다. |
| ② 그룹별 선택 | 공정 7에서 중복 지원 제한이 확인된 그룹마다 제한 범위(그룹 전체, 채용 회차, 허용 건수 등), 이미 낸 건과 열린 건, 고른 건과 이유 | 공정 7이 확인한 제한 범위 안에서 이미 낸 건을 포함해 낼 건을 고른다. 고를 재료로 공정 7의 권고와 평가표, 마감일, 직무를 나란히 보이고 사용자가 정한다. 고르지 않은 건은 서류를 쓰지 않고, 사용자가 접기로 하면 평가함은 「지원안함」, 준비중은 「포기」로 적는다. 제한 문구가 모호하거나 그룹 규칙을 확인하지 못한 건과 「회사 미상」 건은 미해결로 두고, 공정 6·7이 모은 원문과 출처, 확인하지 못한 곳을 보이고 사용자가 정한다. 문구가 없다는 것만으로 허용으로 보지 않는다. |
| ③ 쓸 건 정하기 | 이번에 쓸 건, 대기할 건과 다시 볼 조건, 내려놓을 건과 이유 | 사용자가 지정한 건을 먼저 넣고, 그다음 우선 지원, 지원 순으로 넣는다. 조건부는 조건을 확인한 뒤 넣는다. 관문이 「멈춤」인데 사용자가 진행하기로 한 건은 그 결정대로 넣고 권고 칸에 함께 적는다. 「권하지 않음」 건은 필수 과정 전체에 드는 작업과 기대 효과를 알리고 사용자가 정한다. 「어학 대기」 건은 공정 5(`profile.md` 「목표」)가 정한 어학 시기별 경로대로 대기에 두고, 어학 결과가 나오면 공정 7에서 다시 본다. 내려놓기를 추천하는 때는 마감 안에 필수 과정을 지킬 수 없을 때와 권고가 「권하지 않음」일 때다. |
| ④ 작업 순서와 제출 목표일 | 쓸 건마다 작업 순서, 제출 목표일, 같이 쓰는 묶음 전략 | 사용자가 지정한 건을 먼저 두고, 그다음 마감이 이른 건부터 둔다. 마감이 비슷한 건끼리는 권고가 높고 경력이 닿는 정도가 높은 건을 앞에 둔다. 상시·수시 공고는 마감 전에 서류를 보고 합격자를 정할 수 있으므로 게시일부터 지난 기간을 함께 보이고 사용자와 제출 목표일을 정한다. 같은 묶음 전략([strategy.md](strategy.md))을 쓰는 건은 이어서 쓴다. 제출 목표일은 본인 인증, 첨부 오류, 사이트 접속 지연을 고칠 수 있게 마감일보다 앞에 두고, 회사 홈페이지 접수는 [submit.md](submit.md) 「미리 할 것」을 순서에 넣는다. |
| ⑤ 작업량 | 쓸 건마다 남은 단계, 마감 안에 모두 마칠 수 있는지 | 선행 공정(공정 3~5)이 끝나지 않았거나 평가(공정 7)가 없는 건은 그 작업을 남은 단계에 넣어 따진다. 마칠 수 없으면 단계를 줄이지 않고 SKILL.md 「생략과 시간 부족」대로 어느 건을 내려놓을지 먼저 사용자에게 묻는다. 내려놓을 후보는 권하지 않음, 조건이 풀리지 않은 조건부, 지원, 우선 지원의 순서로 보이고, 사용자가 지정한 건은 마지막에 둔다. |
| ⑥ 미해결 건의 출구 | 조건부, 대기, 그룹 미해결 건마다 다시 물을 때와 마감이 지났을 때의 처리 | 조건이나 규칙이 풀리지 않은 채 마감이 다가오면 다시 사용자에게 묻는다. 「어학 대기(이번 마감 불가)」 건은 [collect.md](collect.md)대로 기본전략 파일의 「다음 채용 확인」에 넣는다. 그 밖의 대기 건은 마감이 지나면 사용자에게 확인한 뒤 평가함이면 「지원안함」, 준비중이면 「포기」로 적는다. |
| ⑦ 갱신 | 새 평가, 마감일 변경, 사용자 지정 변경, 제출, 그룹 선택, 어학 결과가 생기면 해당 행을 그 자리에서 고침 | 지원 기록 표의 상태와 같은 작업에서 맞춘다. 옛 계획은 「변경 기록」 줄로 남긴다. |

**결정:** 계획의 포함, 대기, 내려놓기와 그룹 선택은 사용자가 정한다. Claude는 근거를 붙여 추천하고, 추천과 다르게 정한 결정은 날짜와 함께 적는다.

**완료 기준:** 열린 건마다 계획과 이유가 있고, 중복 지원 제한 그룹마다 고른 건이 제한 범위 안에 있으며, 이번에 쓸 건마다 제출 목표일이 있고, 미해결 건마다 다시 물을 때가 있으며, 사용자가 계획을 확인했다.

## 지원 기록 표

`tracker.md` 한 파일에 표로 관리한다. 파일이 없으면 아래 머리글로 만든다.

```markdown
# 지원 기록
결과 확인 기간: <일 수>

| 번호 | 회사 | 직무 | 채널 | 상태 | 권고 | 지원일 | 마감일 | 다음 할 일 | 다음 할 날 | 폴더 | 메모 |
|---|---|---|---|---|---|---|---|---|---|---|---|
```

- 권고 칸에는 공정 7(`evaluate.md`)의 권고 값을 쓴다. 평가표 항목의 수준은 평가 파일에 있고 이 칸에 옮기지 않는다. 관문이 「멈춤」이어서 권고를 매기지 않은 공고는 「—」를 쓰고 메모에 걸린 관문을 적는다. 평가한 뒤에 멈춤이 된 공고(마감이 지남 등)는 매겨 둔 권고를 그대로 두고, 평가 파일이 그 값을 「참고값」으로 적는다.
- 결과 확인 기간은 사용자가 정한 값이다. 비어 있으면 처음 필요할 때 한 번 묻고 적는다.
- 채널: 사람인, 원티드, 리멤버, 잡코리아, 회사 채용 페이지, 추천, 헤드헌터, 공공기관 등
- 날짜는 YYYY-MM-DD
- 칸 안에 `|`와 줄바꿈을 쓰지 않는다. 긴 내용은 지원 폴더의 파일에 쓰고 메모에는 한 줄만.
- 공고나 메일의 문장을 그대로 옮기지 않는다. 사용자가 확인한 사실만 짧게 쓴다.

## 상태

상태 칸에는 아래 값만 쓴다. 날짜, 괄호 설명, 권고 같은 꾸밈을 넣지 않는다. 그런 내용은 메모 칸에 쓴다.

| 상태 | 뜻 |
|---|---|
| 평가함 | 공고 평가만 함 |
| 어학 대기 | 어학 점수 조건이 풀리지 않아 기다림(`evaluate.md` 「관문」). 끝난 상태가 아님 |
| 지원안함 | 평가 뒤 사용자가 지원하지 않기로 함 |
| 준비중 | 서류 작성 중 |
| 지원함 | 제출을 확인함 |
| 서류통과 | 서류 합격 연락 |
| 필기·과제 | 인적성, NCS 필기, 코딩테스트, 과제, AI역량검사 진행 |
| 1차면접 | |
| 2차면접 | |
| 최종면접 | 임원 면접 등 |
| 처우협의 | 오퍼·연봉 협의 |
| 합격 | 입사 확정 |
| 불합격 | 회사가 탈락 통보 |
| 무응답 | 후속 연락 두 번 뒤에도, 또는 60일 넘게 변화 없이 소식 없음. 사용자가 승인해 바꾼다 |
| 포기 | 준비하거나 지원한 뒤 사용자가 접음 |
| 오퍼거절 | 사용자가 오퍼를 거절함 |

규칙:
- 「지원함」은 사용자가 제출했다고 말했거나, [submit.md](submit.md)대로 제출한 뒤 접수 완료 화면이나 지원 내역 페이지에서 접수를 확인했을 때만 쓴다. 지원일은 실제 제출 날짜로 쓴다. 다음 할 일은 「결과 확인」, 다음 할 날은 지원일에 결과 확인 기간을 더한 날로 쓴다. 다른 대화나 에이전트가 제출했다고 보고한 것은 사용자에게 제출 여부를 확인한 뒤 쓴다.
- 「지원안함」은 사용자가 지원하지 않기로 말했을 때만 쓴다. 평가의 권고만으로 바꾸지 않고, 권고는 권고 칸에 둔다.
- 「어학 대기」 건은 어학 결과가 나와 공정 7에서 다시 판정하면 「평가함」이나 「준비중」으로, 사용자가 접으면 「지원안함」으로 바꾼다. 이 경우를 뺀 상태는 뒤로 되돌리지 않고, 잘못 적었으면 메모에 정정 이유를 쓴다.
- 합격, 불합격, 무응답, 포기, 오퍼거절, 지원안함은 끝난 상태다. 같은 회사에 다시 지원하면 「재지원」대로 새 행을 만든다.
- 새 행을 만들기 전에 같은 회사·직무 행이 다른 채널(직접 지원, 다른 헤드헌터)로 있는지 본다. 있으면 어느 채널로 갈지 사용자가 정한다. 한 자리에 두 채널로 들어가면 양쪽에서 신뢰를 잃는다.
- 메일이나 문자 내용을 붙여넣어 상태를 바꿀 때는 사용자에게 한 번 확인한다. 발신자가 회사나 채용 시스템인지 사용자에게 묻고, 확인되지 않으면 바꾸지 않는다(SKILL.md 규칙 1).

## 재지원

끝난 상태의 회사에 다시 지원하면 새 행을 만든다. 재지원 제한은 공정 7(`evaluate.md` 「관문」)의 판정을 따른다. 이전 행이 있으면 그 지원 폴더의 `결과.md`와 `면접복기-<차수>.md`를 공정 10(기업 분석)과 공정 11(전략)의 입력으로 가리키고, 회사 채용 사이트에 남은 예전 지원서와 지금 서류가 어긋나지 않는지 확인하라고 사용자에게 알린다.

## 후속 연락

| 상태 | 첫 연락 | 이후 | 최대 |
|---|---|---|---|
| 지원함 | 지원 7~10일 뒤 | 7일마다 | 2회, 그 뒤 무응답 |
| 서류통과~최종면접 | 연락 받은 날 안에 회신 | 3일마다 | 제한 없음 |
| 면접 뒤 | 다음 날 감사 메시지(외국계는 흔함, 국내 기업은 선택) | 결과 예정일이 지나면 1회 | |

연락 시점과 횟수는 근거가 있는 값이 아니라 기본값이므로 사용자가 바꿀 수 있다고 알린다.

- 첫 메일: 제목 → 직무와 지원일 → 내가 줄 가치 하나(수치) → 이 회사에 맞춘 사실 하나 → 가볍게 진행 상황 문의와 통화할 수 있는 때. 보통 짧게 쓴다(150단어, 한국어 400자 안팎이 흔한 분량이고 판정 기준이 아니다). "혹시나 해서 연락드립니다" 같은 말 대신 용건을 바로 쓴다.
- 회사가 알린 결과 예정일이나 발표일이 지난 뒤의 연락은 채용 여부를 알려 달라고만 쓰고 법 조항을 들지 않는다.
- 내용은 제출한 서류와 기업 분석에 있는 것만 쓴다. 서류에 없는 경력·수치를 새로 넣지 않는다.
- 헤드헌터를 거친 지원은 후속 연락을 헤드헌터에게 한다. 고객사를 모르면 회사 이름을 물어보라고 권한다. 알게 되면 회사 칸을 고치고 같은 회사 행이 있는지 다시 본다.
- 두 번째는 다른 각도로 쓴다. 세 번째는 쓰지 않고, 무응답 처리·다른 연락처·우선순위 낮추기 중 사용자가 고른다.
- 메일·메시지는 초안만 쓴다(SKILL.md 규칙 5). 사용자가 보냈다고 확인한 연락만 기록한다.
- 국내 공채는 결과 발표일이 정해져 있다. 발표일 전에는 후속 연락을 권하지 않는다.

## 대화를 시작할 때

사용자가 지원 현황을 묻거나 구직 작업을 시작하면 대화마다 처음 한 번 오늘 날짜 기준으로 알려 준다.
- 마감이 7일 안에 남은 「평가함」, 「준비중」. 마감이 이미 지난 「준비중」은 따로 한 줄로 알린다
- 마감이 이미 지난 「평가함」: 목록으로 보이고 「지원안함」으로 정리할지 묻는다(전부 / 골라서 / 그대로). 마감이 「상시」나 「채용시」인 공고는 넣지 않는다. 사용자가 승인한 행만 바꾸고, 그 행의 평가 파일은 [evaluate.md](evaluate.md) 「12. 사용자 결정과 갱신」대로 고친다
- 「다음 할 날」이 지났거나 오늘인 행
- 그 가운데 다음 할 일이 「결과 확인」인 「지원함」 행: 지원 내역 페이지나 메일에서 결과가 왔는지 확인하자고 한 줄로 제안한다. 불합격을 알리지 않는 회사가 많으므로, 결과가 없으면 「후속 연락」 표대로 연락할지 사용자가 정한다. 아래 60일 항목에도 해당하면 60일 항목만 쓴다
- 「지원함」부터 「처우협의」까지의 상태로 60일 넘게 변화 없는 행: 한꺼번에 무응답으로 정리할지 사용자에게 묻는다(전부 / 골라서 / 그대로). 제출하지 않은 「평가함」, 「준비중」은 넣지 않는다. 무응답 처리는 사용자가 승인한 뒤에만 한다
- `work/지원계획.md`가 있으면 계획과 어긋난 행과 「여러 곳 지원 계획」 ⑥의 미해결 건(다시 물을 때가 된 건 포함)
- 「어학 대기」 행: 어학 결과가 나왔으면 공정 7에서 다시 판정하자고 알린다
- 프로필 「행동으로 드러난 선호」의 분석일 뒤에 지원일이 적힌 행이 있으면, 그 절을 다시 볼지 한 줄로 묻는다([tracker-analysis.md](tracker-analysis.md) 「행동으로 드러난 선호」). 그 절이 비어 있거나 분석일이 없으면, 지원일이 적힌 행이 있을 때 분석을 할지 한 번 묻는다

## 결과 기록

- 회사에서 받은 피드백은 해석하지 않고 들은 그대로 지원 폴더의 `결과.md`에 추가한다. 이전 기록은 고치지 않는다.
- 결과를 기록할 때 도달한 전형 단계와 날짜를 적는다. 회사가 무엇을 중요하게 본 것 같은지는 사용자에게 묻고 들은 그대로 적는다. 다음에 무엇을 다르게 할지는 묻지 않고, 기록(`검토.md`, 면접 복기, 받은 피드백, 제출본)에서 근거를 찾아 초안을 써서 보이고 사용자가 고치게 한다. 사용자가 고친 말을 적는다.
- 면접에서 떨어진 건은 [interview.md](interview.md) 「4. 복기」를, 오퍼 단계에서 끝난 건은 [offer.md](offer.md) 「7. 지원 기록」을 함께 가리킨다.
- 제출본은 [submit.md](submit.md)대로 보관된 `제출서류/`를 그대로 둔다. 온라인으로 낸 서류는 회사에 돌려받을 수 없으므로 보관한 제출본이 기준 사본이다.
- 공고를 기억으로 다시 만들지 않는다. `postings/`의 원문을 쓴다.

## 분석 요청

사용자가 요청하거나, 새 결과가 이전에 떨어진 건과 같은 원인을 공유하는 것으로 보이면(Claude가 제안한다) 분석을 한다. 지원 기록 분석(결과 분석, 행동으로 드러난 선호, 부족한 역량과 학습 계획)은 [tracker-analysis.md](tracker-analysis.md)를 읽고 따른다.

## 완료 기준

지원 기록의 상태와 지원 폴더의 제출본이 서로 맞고, 결과가 난 건마다 도달 단계와 피드백이 적혀 있으며, 분석에서 나온 교훈이 사용자의 동의를 받아 다음 지원이 읽는 산출물이나 공정 17이 가져갈 분석 기록으로 넘어갔다.
