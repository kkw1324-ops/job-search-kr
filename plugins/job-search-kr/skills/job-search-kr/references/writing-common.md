# 서류 작성 공통 규칙

## 적용 범위

서류 문구를 쓰는 모든 작업(국문 이력서·경력기술서, 자소서·지원서 문항, 영문 CV·커버레터, 구직 사이트 칸, 회사 양식 칸, 대화에서 제안하는 문구)과 검토 에이전트의 판정이 이 파일을 따른다.
- 서류별 문서(resume-kr.md, essay-kr.md, resume-en.md, site-profile.md, forms.md)에는 그 서류에만 있는 규칙을 두고 여기 규칙은 절 이름으로 가리킨다. 부딪치면 이 파일을 따른다. 문체는 서류의 종류에 따라 [style-essay.md](style-essay.md)의 자소서 문체와 보고서형 문체로 나뉘며, 어느 쪽이든 아래 「문체」의 공통 규칙이 먼저 걸린다. 예외는 둘이다. (가) 영문 서류는 [resume-en.md](resume-en.md)의 관례를 따른다. (나) 구직 사이트의 한 줄 칸에는 괄호와 화살표를 쓰지 않는다([site-profile.md](site-profile.md) 「글쓰기 기준」).

## 칸 용도

칸마다 그 칸이 묻는 것에만 답한다.
- 입사 후 문장(포부, 다짐, 적용 계획)은 칸이 그것을 묻거나 [essay-kr.md](essay-kr.md) 「문항 유형」·「구직 사이트 이력서의 자기소개서」 표의 구조 열에 입사 후 단계가 있는 칸에만 쓴다. 커버레터는 [resume-en.md](resume-en.md) 「커버레터」의 셋째 문단에 쓴다.
- 이력서 상단 요약, 경력기술서, CV Summary, 구직 사이트 소개글·경력 칸, 양식의 경력·프로젝트 칸에는 입사 후 문장을 쓰지 않는다. 자소서의 경력 칸에서, 경험에서 보인 판단 기준이 지원 직무의 어느 업무에 닿는지를 적은 문장은 입사 후 문장이 아니다([essay-kr.md](essay-kr.md) 「기본 구조」의 맺음).
- 칸의 마지막 문장은 「문체」의 문장 연결을 따른다.
- 칸을 줄일 때는 결과·수치 문장을 남기고 칸 용도 밖 문장을 먼저 뺀다.

## 사실 대조

사실의 원천은 `profile/profile.md`다(SKILL.md 규칙 2). 경험 카드(`profile/stories/`의 파일)의 수치는 profile.md에 같은 수치가 있을 때만 쓴다. 아래를 모두 맞춰 불일치를 0건으로 만든다.
- **항목**: 날짜, 회사명, 직함, 수치, 도구, 자격증, 연락처를 프로필과 하나씩 맞춘다. 기간은 시작일과 끝 날짜로 개월 수를 다시 계산하고, 입사일과 기준일은 일 단위로 계산한다(프로필에 일이 없으면 묻는다). 원천끼리 어긋나면 멈추고 묻는다.
- **서류 간 일치**: 같은 회사에 내는 서류(이력서, 경력기술서, 자소서, 양식, 영문 CV, 커버레터)와 문항끼리 기간, 수치, 역할 범위, 도구, 회사명, 팀 규모를 맞추고 다르면 프로필 값으로 통일한다. 원티드·리멤버·LinkedIn 프로필을 쓰면 사용자가 붙여넣은 내용과도 맞춘다.
- **표기 통일**: 같은 대상(제품, 도구, 용어)은 한 문서 안에서, 그리고 같은 회사에 내는 서류 사이에서 하나의 이름으로 쓴다. 이름은 직무 프로필 용어표의 표기를 먼저 따르고, 용어표에 없으면 사용자가 쓰는 이름을 따른다. 사용자가 말한 이름이 업계에서 통하지 않는 표기이면 문서에는 용어표의 표기를 쓰고 사용자에게 알린다.
- **없다고 적기 전**: 사실이나 값을 「없음」으로 적기 전에 프로필, 카드, 자기 분석 기록, 작업 기록에서 찾고 찾아본 곳을 적는다. 기록에 있는 내용을 사용자에게 다시 묻지 않는다.
- **행동의 범위**: 사례 문장마다 주어(제안 / 결정 / 직접 수정), 빈도(한 번 / 늘), 사건 순서를 프로필 기록과 맞춘다. 대화에서 받은 답과 결정은 문장에 넣기 전에 프로필에 먼저 적는다.
- **본인 기여 범위**: 프로그램·도구를 만들었다는 문장은 저장소 기록(작성자, 커밋, 결과물 형태)과 맞춘다. 카드 「④ 부분별 기여」에 그 부분의 기여가 이미 적혀 있으면 그 판정을 따르고 사용자에게 다시 묻지 않는다. 적혀 있지 않을 때만 저장소 주소나 `git log` 출력을 사용자에게 받는다. 사용자 말과 기록이 다르면 이 순서로 정한다.
  1. 사용자가 말한 기준으로 다시 센다.
  2. 줄 수 비중만으로 판정하지 않고 코드 성격(무엇을 새로 짰나)과 전후 화면으로 확인한다.
  3. 그래도 다르면 기록 범위로 쓰고 기록을 사용자에게 보여 준다.

  서류의 주어는 확인된 범위의 단어(기획, 정의, 검토, 담당)로 쓴다. 여러 부분으로 된 시스템은 카드 「④ 부분별 기여」의 판정(만듦, 다시 만듦, 확장, 지시, 검토, 조율, 참여, 내 것 아님)대로 부분마다 쓰고, 「처음부터 혼자 만들었다」처럼 범위를 부풀린 표현 대신 맡은 부분을 정확히 쓴다.
- **자격이 필요한 판단**: 자격·면허가 필요한 판단(예: 구조 계산 승인, 세무 신고 대리, 의료 판단)은 지원자가 정했다고 쓰지 않는다. 그런 판단이 든 사례는 쓰기 전에 자격이 필요한지 사용자에게 묻고, 필요하면 지원자의 몫(검토 의뢰, 결과 반영)으로 쓴다.
- **바꿔 써도 되는 범위**: 순서 바꾸기, 동의어, 넓은 역할 중 한 측면 강조, 같은 뜻의 공고 용어는 쓴다. 학교·연구 경험을 실무처럼 쓰기, 인접 업무를 공고의 전문 용어로 쓰기, 팀 성과를 본인 중심으로 쓰기는 사용자에게 유지·완화·삭제를 묻는다. 없는 경험, 해 본 적 없는 도메인, 직함, 기간, 수치는 만들지 않는다.
- **공고 맞춤의 한계**: 검토·관리였던 일을 직접 한 일로 키우지 않는다(「경력 줄 기준」).
- **사례 문장의 뜻**: 경험 카드의 「⑤ 사용자의 말」 방향으로 쓰고 「⑦ 경계」의 쓰지 않을 것의 뜻으로는 쓰지 않는다([self-analysis.md](self-analysis.md) 「3. 의도 받기」).

## 경험 카드

사례를 쓰는 자리(자소서 문항, 경력기술서 프로젝트, 이력서 상단 요약의 대표 성과)는 경험 카드(`profile/stories/`의 파일)의 필수 칸(①, ②, ④, ⑤와 그 문항이 필요로 하는 칸)이 모두 찬 사례만 쓴다. 칸, 채우는 순서, 작업 기록 찾기, 질문 규칙은 [self-analysis.md](self-analysis.md) 「4. 경험 카드」에 있고, 자소서에서 확인하는 시점은 [essay-kr.md](essay-kr.md) 「경험 카드 게이트」다.

## 서류에 쓰지 않는 것

|---|---|
| 내부 프로젝트 코드·과제 번호·사내 관리번호 같은 사내 식별자 | 품목·과제와 업무(「결제 시스템 개편」「예산 편성」) |
| 회사 내부 실수·문제(구버전 배포, 정산 오류, 이중 발주, 관리 부실) | 상태(「수작업으로 관리」), 기능과 결과 |
| 경력 줄·경력기술서 배경·결과 칸의 회사 고유 기능·모듈 이름, 만든 것의 목록 | 업무 이름. 세부는 면접 예상 질문 표 |
| 경력 줄 문장 안의 도구·기술 스택 나열 | 경력기술서 「사용 기술·도구」 칸, 이력서 기술란 |
| 경력 항목·과제 소제목의 기간 | 이력서 경력란의 기간 칸 |
| 퇴사·이직 사유 | 면접 답([interview.md](interview.md)). 회사 양식이나 지원 화면이 칸으로 물을 때만 아래 규칙대로 쓴다 |
| 프로필의 「(확인 필요)」 줄과 「서류 사용 금지」 표시 사실 | 사용자 확인을 받은 사실 |
| 「처음 맡았다」「처음 다뤘다」 같은 첫 경험 표현 | 배운 것을 적용한 행동과 결과. 공고가 학습 경험을 물으면 익힌 방법과 적용 결과 |
| 논문·자료에서 찾은 결과를 본인 결과로 쓴 문장 | 본인이 바꿔 비교한 설계. 일반 원리는 예상질문.md |

퇴사·이직 사유 규칙: 칸이 물으면 프로필 「목표」의 이직 대전제·이직 사유 방향에 따라 그 회사에 맞춘 한 문장을 쓰고, `전략.md` 「뽑고 싶은 사람」과 기업분석의 회사 사실 하나에 잇는다. 다른 회사 이름으로 바꿔도 맞는 문장(치환 시험 실패)은 다시 쓴다. 현 회사 비난과 처우는 넣지 않는다.

## 수치

- 경력 항목(이력서, 경력기술서)마다 수치나 대체 근거를 하나 이상 둔다(건수, 시간, 비율, 금액, 전후 값). 자소서 칸에는 그 칸의 메시지를 증명하는 수치만 쓴다.
- 숫자가 없으면 이 순서로 대체 근거를 찾는다: (1) 전후 변화(정성이라도 가능) (2) 전체 가운데 내 몫(「12개 중 8개 담당」) (3) 정성 근거(내가 만든 양식을 팀이 계속 씀, 상사의 평가) (4) 작고 셀 수 있는 숫자, 범위, 빈도(「한 달간 반품 사유 15건 분류」가 「다수 건 처리」보다 낫다).
- 수치가 없는 결과에는 그 결과를 무엇으로 확인했는지를 한 문장 붙인다(전후 대조, 교차 검증, 다른 원인 배제, 그 뒤 같은 문제가 다시 나지 않은 기간, 남긴 기준을 팀이 계속 쓰는지). 확인 방법이 없으면 결과는 주장으로 읽힌다. 기록에 있는 확인만 쓴다.
- 값이 없다고 사용자에게 묻기 전에 셀 수 있는 값은 먼저 직접 센다. 프로필, 카드, 작업 기록, 저장소 기록(커밋, 설계·결과 문서)에서 건수, 기간, 개수를 세고 계산식과 출처를 적는다.
- 사용자가 말했거나 확인한 값, 또는 위처럼 기록에서 직접 센 값만 쓴다. 「대부분」을 95%로 바꾸지 않는다. 그래도 없으면 「추산값 추천」을 따른다. 자소서 칸에서는 그 칸의 메시지에 필요한 수치일 때만 추산값을 추천하고, 그렇지 않은 수치는 빼고 쓴다.
- 수치에 붙은 「약」은 소제목, 본문, 요약에서 같게 둔다.
- 면접에서 1분 안에 설명하지 못하는 수치는 쓰지 않는다(「1분 설명 시험」).

## 추산값 추천

수치가 없으면 AI가 추산값을 추천하고, 사용자가 확인한 값만 쓴다.
1. 프로필·카드·작업 기록에서 이어지는 사실(건수, 빈도, 건당 시간, 인원, 기간)을 모은다. 하나도 없으면 추천하지 않고 무엇을 알면 추산할 수 있는지 묻는다.
2. 계산식으로 추천한다. 예: 「월 약 20시간 = 월 약 40건(카드 <이름>) × 건당 약 30분」. 근거마다 출처를 적고, 사실로 채우지 못한 입력값은 「가정」으로 표시해 범위로 쓴다.
3. 범위가 나오면 낮은 쪽을 추천한다. 업계 평균·남의 사례만으로 개인 성과를 정하지 않는다.
4. 추천값, 계산식, 가정을 보이고 받아들일지, 고칠지 묻는다. 확인 전에는 서류에 `[수치 확인 필요] (추천: 약 N, 계산식)`으로 둔다.
5. 확인받은 값은 「약 N」(영문 "approx. N")으로 쓰고 「본인 추산」·"self-estimated" 같은 출처 표기는 붙이지 않는다. 추산이라는 사실과 계산식은 면접 예상 질문 표에 남겨 면접에서 추산이라고 먼저 밝히게 하고, 사용자가 고친 값과 날짜는 프로필에 적는다.
6. 운영 전·사용 전 기능의 효과(절감 시간, 사용자 수)는 추천하지 않는다.

## 경력 줄 기준

이력서·경력기술서·구직 사이트의 경력 항목(■ 소제목 아래 줄)과 영문 CV의 Work Experience에 적용한다.
- **업무 + 결과**: 맡은 일에 결과를 붙인다(행동 + 범위 + 결과). 결과에는 수치나 「수치」 절의 대체 근거를 쓴다. 결과를 만든 핵심 수단(방법, 도구)은 한 줄에 하나까지 쓴다. 예: 「주문 API 응답 지연 원인을 분석해 캐시를 도입, 평균 응답 시간 1.2초→0.4초(사내 모니터링 기준)」.
- **JD 수준 용어**: 채용 공고 직무 기술에 쓰이는 업계 용어로 쓴다. 「일정 조율」「피드백 정리」 같은 기본 소통은 전문 업무에 합친다.
- **동사로 끝내기**: 대상 업무 없이 「담당」「참여」「지원」「노력」만으로 줄을 끝내지 않는다. 직접 한 동작은 동사(작성, 검토, 결정, 개발)로 쓴다. 영역만 맡았으면 대상 업무 뒤에 범위 단어를 둔다(「결제 모듈 코드 리뷰 담당」「월 결산 검토 담당」).
- **묶음 단위**: 한 업무 안의 결정과 같은 성격의 일(협력사 결과물 검토, 외부 문의 대응)은 한 줄로 묶고, 업무 흐름의 단계를 줄마다 옮기지 않는다.
- **항목 선별**: 단편적이고 짧은 안건은 경력 항목으로 세우지 않고 자소서 소재로 보낸다.
- **범위와 깊이**: 사실보다 넓게 쓰지 않는다. 범위를 좁힐 때도 줄을 쪼개거나 세부를 늘리지 않고 단어(작성 / 검토 / 담당)로 맞추며, 단어는 채용 공고의 표기를 고른다(「검수」 대신 「검토」). 「담당」은 대상 업무 뒤에 붙는 꼴로만 쓴다.
- **줄이기**: 관련성, 고유성, 자소서가 그 줄에 기대는지를 보고 가장 약한 줄부터 뺀다. 섹션 순서대로 자르지 않는다.

## 줄 수

아래 줄 수는 서류 종류의 관례이고 판정 기준이 아니다. 쓸 내용이 모자라면 줄 수를 맞추려고 줄을 늘리지 않는다.

| 서류·칸 | 줄 수 |
|---|---|
| 이력서 상단 요약 | 연결 문장 1~2개 + 대표 성과 3줄([resume-kr.md](resume-kr.md) 「상단 요약」) |
| 이력서·사이트의 경력 항목(묶음) | 묶음당 4~5줄 |
| 목표 직무와 먼 경력, 오래된 경력 | 한 묶음 2~3줄로 줄인다 |
| 경력기술서 프로젝트의 「본인이 한 일」 | 3~5줄 |
| 영문 CV 역할 | 3~6줄(영문 관례) |

## 문체

서류에 따라 문체가 둘로 나뉜다. 자소서는 이어 쓰는 서술(자소서 문체), 이력서 요약·경력 줄·경력기술서·사이트 경력 칸은 짧고 일정한 틀(보고서형 문체)이다. 각 기준과 예시는 [style-essay.md](style-essay.md)에 있고, 두괄식·고정 순서·기계적 서술은 보고서형에만 걸린다. 아래는 두 문체에 모두 걸리는 공통 규칙이다.

- **어조**: 팀장에게 결과를 보고하는 실무자의 말투로 쓴다. 성격의 이름표(「제 장점은 ~것입니다」) 대신 그 성격이 보이는 사실을 쓴다. 대화에서는 사용자의 용어와 문장 길이를 가져온다.
- **본보기**: 자소서는 쓰기 전에 사용자가 고른 본보기 원문(`profile/본보기/`)과 프로필 「문체」를 읽는다. 본보기의 내용과 수치는 가져오지 않는다([style-essay.md](style-essay.md) 「본보기와 사용자 문체」). 본보기가 없다는 사용자 결정이 프로필 상태표에 있으면 「문체」만 읽는다([self-analysis.md](self-analysis.md) 「문체와 본보기」 5). `profile/잘못쓴사례/`는 본보기로 읽지 않는다.
- **문장 나누기**: 한 번 읽어 뜻이 막히는 문장은 나눈다. 절 사이 쉼표가 셋 이상(같은 자격의 어구를 나열하는 쉼표는 제외)이거나 접속어(그리고, 또한, 이를 통해, 그 결과)가 둘 이상이면 확인할 신호이고 통과 기준은 아니다. 무엇을 했나 → 왜 했나 → 결과로 역할을 나누고 인과 연결어(그래서, 때문에) 하나는 남긴다.
- **문장 연결**: 칸 안의 문장마다 「앞 문장에서 왜 이 문장이 나오나」를 한 줄로 댈 수 있어야 한다. 대지 못하면 두 문장을 잇는 사실(그 일이 생긴 자리, 배경)을 앞에 넣거나 문장을 뺀다. 「대신」, 「같은 방식으로」, 「~처럼」으로 끊긴 곳을 덮지 않는다. 칸의 순서와 마지막 문장은 [essay-kr.md](essay-kr.md) 「기본 구조」와 「맺음」을 따른다. 마지막 문장은 첫 문장의 답을 회사 업무나 직무와 닿는 사실에 잇고 앞 문장을 교훈으로 되풀이하지 않는다. 입사 후 문장을 허용하지 않는 칸은 그 칸의 판단 기준이 직무의 어느 업무에 닿는지를 잇는 사실로 끝내고(짧은 칸은 결과로 끝낸다), 소제목이 있으면 소제목의 사실로 돌아간다.
- **문단 연결**: 문단이 둘 이상인 칸은 한 사람이 쓴 한 편의 글로 읽혀야 한다. 문단 첫 문장은 그 문단의 요지를 말하되, 앞 문단이 세운 것(주장, 대상, 남긴 물음)을 받아 넘어간다. 문단마다 새 주제로 다시 시작하면 칸의 주장이 하나로 모이지 않고 여러 글을 이어 붙인 것처럼 읽힌다. 칸 전체를 처음부터 끝까지 꿰는 한 줄을 댈 수 있어야 하고, 끝 문단은 첫 문단이 연 것을 닫는다. 다음 문단이 받을 것이 없으면 앞 문단 끝에 받을 사실을 두거나 문단 순서를 바꾼다. 「이처럼」, 「이러한 경험을 바탕으로」 같은 접속 구로 끊긴 곳을 덮지 않는다. 따로 나뉜 칸이나 항목 사이에는 적용하지 않는다. 설계는 [essay-kr.md](essay-kr.md) 「④ 칸 설계」의 문단 연결을 따른다.
- **사실과 문체**: 사실이 먼저다. 문장 흐름을 맞추려고 수치를 빼거나 흐리지 않고, 사람이 쓴 글처럼 보이려고 세부를 지어내지 않는다. 샘플 글의 내용과 수치는 가져오지 않는다.
- **고친 뒤 점검**: 문장을 빼거나 바꿀 때마다 지시어(이, 그, 이런)의 앞말이 남아 있는지, 칸끼리 같은 사례를 새 행동·판단 없이 다시 쓰지 않았는지 본다([essay-kr.md](essay-kr.md) 「④ 칸 설계」의 칸 사이 중복).

## 지원 업계의 말

- 역량, 업무, 산출물 이름은 지원 직무의 직무 프로필 용어표(`work/직무분석/<직무>.md`, [job-analysis.md](job-analysis.md))에서 가져온다. 용어표의 「프로필의 해당 사실」이 빈 표현과 판정이 「없음」인 표현은 경험을 주장하는 문장에 쓰지 않는다.
- 경험 문장은 직무 프로필 「업무 방식」대로 쓴다: 무엇을 어떤 기준(업계가 보는 기준·규정의 이름)으로 판단했는지, 업계가 일하는 순서(받은 것 → 정한 것 → 넘긴 곳)대로, 업계가 잘했다고 보는 결과로 적는다. 프로필 사실이 용어표 줄과 맞으면 그 줄의 표현을 쓴다. 맞출 사실이 프로필에 없으면 지어내지 않고 기록에 있는 범위의 말로 쓴다.
- 업계 표현이 사실보다 넓으면 사실 쪽 단어를 쓴다. 같은 사실에 업계 표현이 여럿이면 대상 공고에 쓰인 것을, 없으면 여러 공고에서 더 자주 나온 것을 고른다.
- 지원 업종이 본업과 다르면 현장 용어를 억지로 번역하지 않고 자리에 따라 쓴다.

| 자리 | 본업 용어(예: ERP 모듈명, 회계 계정과목, 광고 노출 지표) |
|---|---|
| 경력 줄, 소제목, 이력서 상단 요약, 프로젝트 이름 | 용어표 「쓰지 않을 표현」의 짝으로 바꾼다. 짝이 없으면 면접 예상 질문 표로 옮긴다 |
| 자소서 서술 문장 | 아래 「말을 고르는 순서」를 따른다. 본업 용어를 일반어로 바꾸어 기술 내용을 지우지 않는다 |
| 업종이 같은 지원의 모든 자리 | 업계 용어를 그대로 쓴다 |

- 업종을 바꾸는 지원은 본업 과제 가운데 지원 직무와 이어지는 것만 프로젝트로 두고, 본업 자체는 경력란 한 줄로 둔다.
- 사용자가 만든 도구의 내부 이름(함수, 모듈, 화면 이름)은 면접 예상 질문 표에 두고, 본문에는 그 도구가 다룬 업무의 대상과 기준, 검증한 내용, 결과를 쓴다. 업무 쪽의 기술 내용(보정한 항목의 이름, 연결한 칸의 범위, 대조한 문서)은 내부 이름이 아니므로 본문에 남긴다.

### 말을 고르는 순서

서술 문장에서 경험의 대상, 기준, 방법, 결과를 가리키는 말은 다음 순서로 고른다.

1. 지원 업계가 같은 일이나 같은 대상을 부르는 이름이 있고 사용자의 사실이 그 뜻에 맞으면, 그 이름을 쓴다. 이름은 직무 프로필의 용어표와 「쓰지 않을 표현」의 짝, 직군 지식 파일의 「현업의 말」 절에서 찾는다. 이 절은 사용자별로 만든 직군 파일(작업 폴더의 `work/검토단-근거/지식-직무-<직군>.md`)에 있고, 만드는 방법은 [panel/지식-직무.md](panel/지식-직무.md)와 [job-analysis.md](job-analysis.md) 「직군 지식 파일 확인」이 정한다.
2. 지원 업계에 대응하는 이름이 없거나 사실이 그 뜻보다 좁으면, 카드와 프로필에 적힌 본업 용어를 그대로 쓰고 처음 나올 때 한 번 뜻을 붙인다(예: 「리드타임(주문부터 납품까지 걸리는 기간)」). 약어는 처음에 풀어 쓴다.
3. 일반어로 바꾸는 것은 독자 직무의 팀장이 모르는 부품·장비의 고유 이름뿐이다. 이때도 기준, 규격, 수치, 문서의 이름은 남긴다.
4. 지원 업계의 말이 사실보다 넓으면 쓰지 않는다. 공고에서 가져온 말은 사용자의 사실에 붙일 수 있을 때만 경험 문장에 쓴다. 입사 후 문장에서는 그 말이 가리키는 업무를 직무 프로필과 기업 분석으로 확인한 만큼만 쓴다.

### 실무 문장의 요소

이 절은 쓰기로 한 문장의 말을 뭉개지 않게 하려는 것이다. 사실을 더 모으거나 카드의 사실을 모두 싣게 하는 근거가 아니며, 어떤 장면과 사실을 쓸지는 칸의 메시지가 정한다([essay-kr.md](essay-kr.md) ④).

경험을 주장하는 문장은 아래 넷 가운데 그 문장이 다루는 것을 이름으로 적는다. 카드나 프로필에 이름이 있는 것을 뭉뚱그린 말(리스트, 프로그램, 장비, 기준, 값, 보정값, 관련 부서)로 바꾸지 않는다.

- **대상**: 무엇을 다뤘는가. 문서, 도면, 부품, 설비, 시스템의 이름과 규격·크기.
- **기준**: 무엇에 비추어 확인하거나 정했는가. 대조한 문서, 규격·표준의 이름, 기준값.
- **방법**: 어떻게 했는가. 지원 업계가 부르는 방법 이름이 사실과 맞으면 그 이름.
- **결과**: 무엇을 어떻게 세거나 재었는가. 문장에 쓰는 수치는 카드와 프로필의 값 그대로 쓰고 「많이」, 「크게」로 바꾸지 않는다.

- 「확인했습니다」, 「검토했습니다」, 「점검했습니다」, 「조절했습니다」로 끝나는 문장은 대상과 기준이 같은 문장이나 바로 앞 문장에 있을 때만 쓴다.
- 요소가 카드와 프로필에 없으면 지어내지 않고, 그것을 채우려고 묻지도 않는다. 기록에 있는 범위의 말로 쓴다. 묻는 경우는 [essay-kr.md](essay-kr.md) ③의 6번이 정한다.
- 대외비여서 이름이나 기능을 쓸 수 없는 대상(사용자의 결정, 카드 「⑦ 경계」)은 역할을 가리키는 말로 쓴다(예: 「물류 시스템의 장비 한 대」). 이것은 뭉갠 대상으로 보지 않는다.
- 여러 안을 비교해 고른 판단은 안의 내용을 늘어놓지 않아도 된다. 여러 안 가운데 골랐다는 사실과 고른 기준이 한 구절에 있으면 충분하고, 안마다의 내용은 면접에서 답할 몫이다.
- 글자 수가 모자라면 메시지를 받치는 문장의 요소를 지우지 않고 배경 설명과 수식어, 메시지와 먼 문장을 먼저 줄인다.
- 쉬운 글은 문장의 짜임이 쉬운 글이다. 「문체」, 「금지 표현」, 「AI 문체 신호」는 문장의 짜임에 적용하고, 전문 용어를 일반어로 바꾸는 이유로 쓰지 않는다.
- 본인이 직접 한 일과 검토·지시한 일의 구분은 「사실 대조」를 따른다. 전문 용어를 쓴다고 해서 수행 범위가 넓어지지 않는다(예: 협력사가 고친 것을 「조절했다」로 쓰지 않는다). 사용자가 정하고 협력사가 그리거나 만든 일은 카드 「④ 부분별 기여」의 몫대로, 정한 사람과 작업한 사람이 갈리게 쓴다(「~로 바꾸도록 정했습니다」, 「~하게 했습니다」). 몫이 적혀 있지 않은 옛 형식 카드는 카드에 적힌 사용자의 말을 그대로 쓰고 동사를 올리거나 내리지 않는다.

## 확정 문구와 문장 재사용

- 사용자가 확정한 문구(`profile/경력기술서-기준본.md` 「본인이 한 일」, 경력란 확정본)는 칸과 서류가 달라도 글자와 수식어 그대로 옮긴다. 확정 때 뺀 줄이나 수식어를 되살리지 않고, 개별 과제를 따로 쓸 때도 확정된 역할 줄을 그 과제에 맞춰 좁히지 않는다. 자소서의 서술 문장은 확정된 역할 줄 전체를 실어야 하는 자리가 아니다: 칸의 메시지에 필요한 항목만 문장으로 옮길 수 있고, 옮긴 항목의 표기와 수식어는 그대로 둔다. 역할 줄 전체는 이력서와 경력기술서가 맡는다. 예외는 하나다: 업종을 바꾸는 지원에서는 확정 문구 안의 본업 용어만 「지원 업계의 말」 표대로 짝으로 바꾸고 나머지 글자(표기, 수식어, 줄 구성)는 그대로 둔다.
- 사용자가 경력 문구를 새로 확정하면 같은 턴에 `profile/경력기술서-기준본.md`에 반영한다. 기준본은 그때만 고친다.
- 확정 문구가 아닌 문장은 서류 사이(자소서 ↔ 이력서·경력기술서)에 재사용하지 않는다. 사실은 재사용한다.
- 한 서류 안에서 같은 사실은 두 자리까지 쓴다: 요약 칸(이력서 상단 요약, CV Summary)에 한 번, 본문(경력 줄 또는 프로젝트)에 한 번. 두 번째 자리는 문장 틀을 달리한다. 구직 사이트 소개글의 첫 문장은 아래 업무 줄을 되풀이하지 않는다.

## 고쳐 쓸 때 지킬 뜻

검토 제안을 반영하거나 문장을 다듬을 때 적용한다. 고친 문장에서 아래 요소가 원문과 달라지면 뜻이 바뀐 것이다. 사실 오류를 바로잡는 수정이 아니면 적용하지 않고 사용자에게 보인다.
- 가능·의무·부정: 「할 수 있다」「해야 한다」「않았다」「못했다」를 「한다」「했다」로 바꾸지 않는다.
- 인과와 순서: 「~해서」「때문에」「~한 뒤」로 이은 두 사실의 관계를 바꾸거나 없던 관계를 만들지 않는다.
- 한정과 추산: 「약」「일부」「~만」을 빼지 않는다.
- 수치·고유 표현: 숫자, 단위, 회사명, 용어표의 용어, 확정 문구를 바꾸지 않는다.
- 주어와 범위 단어: 주어를 팀에서 본인으로 바꾸거나 범위 단어(작성 / 검토 / 담당)를 넓히지 않는다.
- 고친 뒤 `revision_check.py` 로 원문과 대조한다. `job-writer`는 명령을 실행하지 못하므로 고친 문장의 고치기 전·후를 돌려주고, 메인이 그 반환으로 `work/revise/` 파일을 쓰고 스크립트를 실행한다(입력 `work/revise/<이름>.before.md`·`<이름>.after.md`, 명령 `python3 <스킬 폴더>/scripts/revision_check.py`). 스크립트는 수치와 위 표현의 개수 변화, 바뀐 비율만 잡는다. 걸린 곳은 문장을 다시 읽고 판정한다.

## 금지 표현

좋은 글의 기준은 [style-essay.md](style-essay.md)가 맡고, 아래는 걸린 표현을 오른쪽처럼 바꾸는 방법이다. 검토 에이전트가 낸 대안 문구에도 적용한다.

| 금지 | 바꾸는 방법 |
|---|---|
| 희망형 어미(「~하고 싶습니다」, 「~할 수 있을 것입니다」), 학생 톤(「배우고 싶다」) | 실행형으로 |
| 감상(「뿌듯했습니다」, 「많이 배웠습니다」), 「이를 통해 OO역량을 기를 수 있었습니다」 | 달라진 행동과 결과로 |
| 과정만 있고 결과가 없는 문장, 수치·대상 없는 성과 동사(「효율을 높였습니다」) | 결과와 근거로 |
| 「귀사에서 성장하고 싶습니다」, 「귀사의 비전에 감명받아」, 「최선을 다하겠습니다」, 「열정」, 「어릴 적부터」, 「대기업인 만큼」, 「급변하는 시대」, 「4차 산업혁명」, 「초격차」, 「위기이자 기회」, 경력직의 「새로운 도전과 성장」 | 삭제하고 사실 문장으로 |
| 「적극적인」, 「꼼꼼한」, 「성실한」, 「책임감 있는」, 「도전적인」 같은 성격 형용사 | 그 성격이 보이는 사실로 |
| 「성장 기회 부족」, 「조직 문화의 한계」 같은 이직 사유 표현 | 쓰지 않는다. 면접 답으로(「서류에 쓰지 않는 것」, [interview.md](interview.md)) |
| 「~에 있어서」 | 「~에서」, 「~할 때」 |
| 다각적, 포괄적, 심층적, 혁신적, 체계적, 뛰어난, 극대화, 시너지, 끊임없이, 비유 명사(「무기」, 「밑거름」) | 무엇이 얼마나 달라졌는지, 사실과 수치가 있는 동사로 |
| 사례를 대신하는 말(「다양한 경험을 통해」, 「책임감을 가지고」, 「소통 능력을 발휘해」, 「팀에 기여했습니다」) | 문제, 내 몫, 행동, 결과를 각각 한 문장으로 |
| 자기 비하와 과도한 겸손, 「합격 보장」 같은 결과 약속, 고객 응대형 어미(「~해 드립니다」), 스스로 칭찬하는 상투어(「누가 시키지 않았지만」) | 한 일을 사실 그대로 |
| 비유 동사(메우다, 바로잡다, 짚다, 버리다, 풀다), 「드러난」, 이야기체 도입(이야기체 도입은 보고서형 서류에만 적용) | 메우다·바로잡다 → 수정하다, 짚다 → 확인하다·표시하다, 버리다 → 대신하다, 풀다 → 해결하다, 드러난 → 발견된 |

추상어는 질문으로 바꿔 구체화한다: 책임감 → 끝까지 맡아 마무리한 일은 무엇이었나 / 소통 능력 → 의견이 갈렸을 때 무엇을 해서 결론을 냈나 / 도전 정신 → 해 본 적 없는 일을 맡았을 때 첫 주에 무엇을 했나 / 꼼꼼함 → 남이 놓친 실수를 몇 건 찾아냈나 / 문제해결력 → 원인을 무엇으로 좁혔나 / 성장 → 1년 전에는 못 하던 일 중 지금 하는 일은 무엇인가.

영어:
- passionate about, proven track record, strong track record, leveraged, spearheaded, facilitated, orchestrated, championed, synergy, robust, seamless, holistic, cutting-edge, innovative, perfect fit, excited to, results-driven, move the needle, data-driven, actionable insights, stakeholder alignment, north star, unique opportunity, best practices, demonstrated ability to, hit the ground running, drive results, responsible for, helped, worked on
- 「I am writing to express」, 「I am writing to apply」, 「I am pleased to」, 「I believe I would be a great fit」, 「in today's fast-paced world」
- 사과하거나 자신을 지나치게 낮추는 표현(「I think I could contribute」)
- em dash(—)
- 영문 CV의 인칭대명사(I, my)와 줄글 서술: 주어를 빼고 동사로 시작하는 줄로 쓴다
- 바꾸는 방법: 동사 과거형으로 시작해 한 일과 수치를 쓴다.

## AI 문체 신호

판정 대상은 누가 써도 같았을 틀로 정보가 비었는지다. 콜론, 수치, 「~했습니다」 같은 형식이나 단어 하나는 신호로 보지 않는다. 아래 신호가 겹쳐 그렇게 읽히면 오른쪽처럼 다시 쓴다. 검토 에이전트가 낸 대안 문구와 소제목에도 적용한다.

| 신호 | 대신 쓸 것 |
|---|---|
| 일반화: 본문의 실제 대상(운영 매뉴얼, 설계 기준서)을 범주어(같은 요청, 기준 문서, 근거 자료)로 바꿈 | 본문의 대상 이름 |
| 틀에 박힌 소제목: 칸마다 같은 끝맺음, 습관 선언(「~하면 ~합니다」), 교훈형, 격언형 | [essay-kr.md](essay-kr.md) 「소제목과 문장」 |
| 틀에 박힌 문장: 「단순한 ~가 아니라 ~」, 세 개씩 나열하는 문장의 반복, 일반 교훈이나 업무 이름 없는 다짐으로 끝나는 문단, 칸마다 같은 구조 | 달라진 행동과 결과 |
| 어조 불일치: 실무 보고 대신 신조 선언, 따옴표 속 자기 대사, 중요성 부풀리기 | 「문체」의 어조 |
| 접속어가 문장마다 있음(「또한」, 「뿐만 아니라」, 「나아가」), 명사화 연쇄(「~함으로써 ~를 통한 ~의」) | 「문체」의 문장 나누기 |
| 모든 문장의 길이와 구조가 같음 | 문장마다 한 역할(무엇을 / 왜 / 결과)을 맡겨 길이가 내용을 따르게 |
| 업계·공고에 없는 에이전트 조어나 틀로 직무·역량을 정의함(「핵심역량을 둘로 봅니다」), 용어표에 없는 역량 이름 | 용어표의 표현 |

자소서·메일은 사용자의 문체 기록([profile.md](profile.md) 「문체」)과 비교해 맞추고, 그 밖의 서류와 기록이 없을 때는 [style-essay.md](style-essay.md)의 보고서형 문체와 「문체」의 공통 규칙으로 쓴다. 자소서 특유의 신호(문단마다 같은 틀로 시작, 답마다 방어하는 절, 마무리 선언)는 style-essay.md 「심사에서 보는 신호」에 있다.

## 1분 설명 시험

- 서술형 서류(자소서, 경력기술서, 이력서 요약)를 쓰면서 미끼 문장(면접관이 묻고 싶어 할 수치·판단 문장)을 정한다. 미끼가 적으면 경험 카드 「② 장면」의 판단과 근거, 「③ 관계자별 전후」의 확인한 변화를 문장에 더 드러낸다.
- 미끼마다 아래 공통 꼬리질문 가운데 그 문장을 읽은 면접관이 물을 만한 것을 던져 본다. 기록에 있는 사실로 1분 안에 답할 수 있으면 미끼로 남기고, 답하기 어려운 문장은 위험 문장이라 고치거나 뺀다: 어떤 문제였나 / 왜 그 방법이었나 / 본인 역할은 어디까지였나 / 결과를 어떻게 확인했나 / 다시 한다면.
- 미끼 표(문장 | 예상 질문 | 1분 안에 답할 수 있나), 추산 계산식, 본문에서 뺀 세부는 `applications/<회사>-<직무>/예상질문.md`에만 둔다. 제출 문서에는 넣지 않는다. 서류를 확정하면 미끼 문장과 위험 문장에서 나올 예상 질문을 같은 파일에 남긴다.

## 키워드 반영률

- 키워드 출처: 공고 평가 보고서 「10. 맞춤 계획」의 키워드(필수·높음 요건의 공고 표현이 앞에 온다). 평가가 없으면 공고에서 뽑는다. 공고가 없는 기본 서류는 직무 프로필 용어표([job-analysis.md](job-analysis.md))에서, 자소서의 인재상 키워드는 기업 분석의 키워드 대조표에서 가져온다.
- 키워드마다 넷 중 하나로 표시한다: 들어감 / 동의어로만 들어감 / 빠짐(프로필에 있음) / 빠짐(격차). 핵심 명사가 글자 그대로(조사·어미 차이만 허용) 있으면 「들어감」, 다른 말로 같은 뜻이면 「동의어로만 들어감」이다. 낱말 둘 이상의 키워드는 모든 낱말이 글자 그대로 있어야 「들어감」이다. 동의어뿐이면 사실일 때 공고 표현으로 바꾸고, 격차는 채우지 않는다.
- 근거 문장 없이 키워드만 넣은 문장은 「들어감」으로 세지 않는다. 키워드는 근거 문장 뒤에 문단당 하나까지 둔다. 숨긴 글자와 키워드 나열은 쓰지 않는다.
- 반영률 = 근거 문장이 붙은 키워드 수(「들어감」과 근거 문장이 있는 「동의어로만 들어감」) ÷ (전체 키워드 수 − 격차 키워드 수). 통과 기준이 아니다. 빠진 키워드와 넣을 자리를 보고에 적고, 공고의 핵심 키워드가 근거 없이 많이 빠졌으면 사용자에게 알린다.
- 배치: 프로필에 있는데 빠진 키워드는 경력 줄에 먼저 넣는다. 상단 요약에는 대표 성과에 닿는 키워드만 둔다. 기술란에는 공고 표기 그대로(사실일 때만) 둔다.
- 반영하지 못한 키워드는 면접에서 보완할 항목으로 예상질문.md에 적는다.
